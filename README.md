## 从一个想法，到一份可以检验的成果

你提出目标，Codex 先了解项目的现状；ChatGPT 协助拆解问题、比较方案；Codex 回到真实环境中审查、实现和验证。遇到瓶颈，它们会带着已有证据重新判断下一步。最终，你得到的不只是一个答案，还有一份清楚的结果：**做成了什么，如何验证，哪些问题仍待解决。**

它是一份安装在 Codex 中的协作 Skill，适合希望借助 AI 完成真实项目的人。它不是独立应用，也不会自行提供 ChatGPT 账号或连接。

## 快速开始

### 1 · 先准备好 Codex 和 ChatGPT

你需要能使用 Codex。要让 ChatGPT 实际参与，还需要有可用的 ChatGPT 访问方式；能否自动交流取决于当前环境的工具与权限。服务的使用额度和费用以各自账户及套餐为准。

### 2 · 安装 Skill

打开 Codex，在你要工作的项目中告诉它：

> 请从 `https://github.com/Shaozrrr/chatgpt-codex-collaboration` 的 `skill` 目录安装 `chatgpt-codex-collaboration`，安装前检查已有版本，不要覆盖我的其他文件。安装完成后告诉我如何开始使用。

你也可以参考文末的[手动安装与管理](#手动安装与管理)。安装后请开启新的 Codex 会话，让它发现新增的 Skill。

### 3 · 把目标交给它

在新的会话中，可以这样开始：

> 使用 `$chatgpt-codex-collaboration` 进行深度协作，帮我完善这个项目。先和 ChatGPT 讨论方案，检查项目现状，再实现并用实际结果验收。

对于范围较小的问题，也可以说：

> 使用 `$chatgpt-codex-collaboration` 进行轻量协作，帮我排查这个问题；说明原因、实际检查结果和剩余限制。

轻量与深度决定讨论和验证的范围。你要求 ChatGPT 参与时，两种方式都会以真实交流为目标；如果当前环境无法连接，Codex 应说明限制，提供精简的交接内容，并继续能够独立完成的工作，不会声称讨论已经发生。

## 适合什么时候用

- **开始一个产品**：从需求、约束和取舍出发，形成可执行的方案，再逐步实现。
- **解决反复出现的问题**：整理现象、已经做过的尝试和证据，避免在同一条路上盲目重复。
- **比较方案或改进体验**：明确需要比较的条件，必要时参考已有产品、开源项目和可复用工具。
- **继续长期项目**：保留关键决定、已验证结果和下一步，让中断后的工作有据可循。

## 协作是怎样发生的

小任务可以使用轻量协作；涉及架构、重要取舍或持续遇到瓶颈时，可以使用深度协作。重要阶段会根据实际需要记录目标、方案与测试证据。对于两次条件可比较、且有记录的改进尝试仍无明显改善的情况，工作流会停止继续调整，先整理证据并请求 ChatGPT 复核。它不会把缺少基线的观察、网络故障或工具错误直接算成两次效果失败。

交付时，结果应让你看清：**完成了什么、实际检查了什么、结果如何、还有哪些没有验证。** 这是工作流的目标；具体效果仍取决于任务、工具连接和可获得的证据。

## 使用前需要知道

- **隐私**：讨论方案时可能需要向 ChatGPT 传递必要背景。对于非公开源码、文件、截图和日志，遵循你的授权与工具权限；不要提供密码、密钥或验证码。
- **连接**：自动协作依赖当前环境支持的 ChatGPT 访问方式；如无法连接，可以使用经过处理的简短交接内容继续讨论。Skill 本身不会绕过登录或权限。
- **效果**：测试、benchmark 和对标按任务需要选择。Skill 提供工作方法，不保证每次结果正确，也不保证节省固定比例的时间或 token。

## 好的执行，始于正确的问题

开发一个产品时，我们常常希望 AI 快一点：快一点理解需求，快一点写出代码，快一点把功能做出来。

但项目越复杂，越需要在速度之外，多一层判断。

需求是否真的被理解？眼前的问题是表象，还是根因？一个方案虽然能运行，是否也适合长期使用？修改之后，究竟变好了多少，又引入了什么新的代价？

这些问题，很难靠一次回答解决。

**ChatGPT × Codex Collaboration** 把规划、执行与验收连接成一套持续运转的工作流。它让 ChatGPT 提出完整方案，让 Codex 回到真实项目中核查、实现和测试，再把结果带回讨论，决定下一步。

它希望解决的，是 AI 协作中最容易被忽视的那段距离：**从“有一个想法”，到“知道它为什么可行”，再到“证明它真的有效”。**

## 两种能力，同一个目标

### ChatGPT 负责把路想清楚

在了解项目背景之后，ChatGPT 负责拆解问题、比较选择、提出架构和关键取舍，并把方案细化到可以执行。

一份有用的方案，不应只写“优化性能”或“改善体验”。它需要说清楚：涉及哪些模块，数据如何流转，依赖什么条件，应该按什么顺序实现，以及怎样判断结果是否达到要求。

当现实与预想不一致时，它也需要根据新的证据重新判断，而不是沿着原来的假设继续推演。

### Codex 负责让方案经受现实检验

Codex 从实际项目出发：检查代码与环境，核实接口和依赖，判断方案是否符合用户的目标。

方案合理，就动手实现；存在矛盾或风险，就把具体问题和证据带回讨论。日常实现细节由 Codex 自主处理，架构变化、目标未达、重要成本变化或重大阻碍，才需要重新进入关键决策。

完成之后，Codex 运行测试、检查真实结果，并如实说明哪些要求已经验证，哪些仍然缺少证据。

ChatGPT 不需要假装看到了它没有看到的项目；Codex 也不需要因为方案来自 ChatGPT，就放弃自己的判断。

## 从现场出发，而不是从假设开始

每一次协作，都从项目现在的样子开始。

Codex 会先梳理用户目标、现有实现、运行环境、历史尝试和已知限制，再把必要的信息交给 ChatGPT。事实、推测和未验证的问题会被分开，避免一个猜测在多轮讨论后，被误当成已经确认的前提。

对于继续中的项目，工作流也会保留已经做过的决定：为什么选择这条路线，哪些替代方案已经排除，哪些测试已经通过，下一步真正要解决什么。

这样，对话可以继续，工作不必反复从头开始。

---

## 让方案落到代码，也落到验收

一份计划只有进入真实环境，才开始接受考验。

这个 skill 要求 ChatGPT 给出足够具体的实施路径，并要求 Codex 在接受方案后，将其转化为对应的执行与验收清单。对于每个重要阶段，都应能回答：

**改哪里，为什么改，依赖什么，做完之后如何证明它有效。**

执行过程中，Codex 会优先排查相关问题是否存在共同根因，合理合并修改，再运行有针对性的检查。已经通过、且未受新改动影响的测试，不会为了制造“工作量”而一遍遍重复。

到阶段结束时，再对真实用户路径做必要的集成与端到端验收。

---

## 用 benchmark 看见真正的变化

“感觉更好了”可以是一个起点，但不应该是最终结论。

当任务涉及准确率、速度、视觉体验、稳定性、转换质量或成本时，工作流会先建立适合项目的 benchmark：明确基线、测试素材、衡量指标、通过条件和测量方法。

修改之后，再尽可能在相同条件下比较结果：

- 同一份输入，是否得到了更准确或更完整的输出？
- 延迟缩短时，是否牺牲了质量或覆盖范围？
- 某个问题消失后，是否引入了新的问题？
- 实验环境中的改善，是否也存在于真实应用里？

样本不足、基线缺失或测试条件不同，都需要被明确写出来。**无法比较的数据，不会被包装成提升；未测过的场景，也不会被写成已经通过。**

---

## 必要时，去看已经有人走过的路

一个问题值得认真解决，也值得先看看其他优秀项目如何解决。

当成熟产品、开源项目或现成组件能够为决策提供帮助时，Codex 会研究它们的功能、交互方式、实现思路和适用条件，再将可核实的信息交给 ChatGPT 一起评估。

对标不是简单地罗列竞品，更不是把宣传材料当作测试结果。工作流会尽量区分：

**亲自观察或测试过的表现；官方文档所描述的能力；以及目前还不能确认的部分。**

对于可复用的项目，还要检查许可证、依赖、平台兼容性、维护状态和分发要求。好的方案可以借鉴，但只有适合当前目标，才值得接入。

---

## 不把重复尝试，当成进展

一个问题没有解决，不代表应该立刻再试一次同样的方法。

在重要修改之前，先明确：我们认为原因是什么，这次改变预期带来什么结果，以及什么证据会说明方向不对。

如果方案在可比条件下持续改善，就继续推进；如果数据不足以判断，就先解决测量问题；如果已知限制使目标无法实现，就及时重新选择路径。

默认情况下，**连续两次有依据、条件可比的尝试都没有带来有意义的改善**，Codex 会停止继续调参，把预期、实际结果、已尝试的方法和剩余疑点交给 ChatGPT，重新审视方案。

这不是机械地规定“两次之后必须放弃”。它的意义是：在投入更多时间之前，先回答——**下一次会因为什么而不同？**

---

## 完成，是一项有证据的判断

代码写完了，不等于功能已经完成；一次模拟通过，也不等于真实场景已经验收。

在交付前，Codex 会对照用户的要求和约定的标准，检查实际完成的内容，并将结果交给 ChatGPT 复盘。双方都必须以已有证据为边界，不能从实现意图推断测试成功，也不能把尚未验证的能力写成已经可用。

一份清楚的结果，应当让人看见：

**哪些已经完成并验证，哪些已经实现但仍需验收，哪些问题尚未解决。**

对复杂项目，这种清楚本身就是进展。

## 手动安装与管理

以下命令适用于 macOS 或 Linux 的终端，并将 Skill 安装到**当前项目**的 `.agents/skills` 目录。需要 Git；请在想使用该 Skill 的项目目录运行。

```bash
git clone https://github.com/Shaozrrr/chatgpt-codex-collaboration.git && \
mkdir -p .agents/skills && \
mkdir .agents/skills/chatgpt-codex-collaboration && \
cp -R chatgpt-codex-collaboration/skill/. .agents/skills/chatgpt-codex-collaboration/
```

`mkdir` 在目标已经存在时会报错，避免直接覆盖旧版本；如果它报错，请先检查并备份旧版本，再自行决定如何更新。若复制中断，也请检查目标目录是否完整。安装完成后开启新的 Codex 会话，使用 `$chatgpt-codex-collaboration` 调用；也可在 Codex 的 Skill 列表中查找该名称。

**更新**时，先检查并备份目标目录，再由 Codex 根据上述仓库地址更新；**卸载**时，确认目标目录无其他需要保留的文件后，将对应的 `chatgpt-codex-collaboration` 目录移走或删除。不同系统与 Codex 版本的操作方式可能不同；不熟悉终端时，直接请 Codex 协助即可。
